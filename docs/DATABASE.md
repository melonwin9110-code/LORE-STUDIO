# Модель данных

Автор проекта: **ElpisHeart**. Схема первого выпуска находится в `db/migrations/001_initial.sql`.

## Подготовка и миграции

Docker Compose запускает PostgreSQL 17 с PostGIS. SQL-миграция включает расширение `postgis`, но географические объекты на первом этапе не создаются. У пользователя миграций должно быть право установить это расширение.

Из корня репозитория:

```sh
docker compose up -d --wait db
npm run db:migrate
```

Команда читает `DATABASE_URL` из `.env`. Мигратор последовательно применяет SQL-файлы, отмечает их в `schema_migrations` и использует advisory lock для защиты от параллельного запуска. Каждая миграция применяется в транзакции. Повторный запуск пропускает уже применённые файлы. Применённую миграцию нельзя незаметно переписать: изменения схемы добавляются новым файлом.

## Таблицы

| Таблица | Назначение и основные поля |
| --- | --- |
| `schema_migrations` | Имя применённого файла и служебное время применения. |
| `users` | UUID, имя, уникальный email в нижнем регистре, scrypt-хеш пароля, дата создания. |
| `sessions` | SHA-256-хеш случайного токена, пользователь, срок действия, дата создания. Срок сессии — 7 дней. |
| `auth_attempts` | Хеш ключа ограничения входа, число попыток и срок окна. Значение email в таблице не хранится открыто. |
| `projects` | UUID, владелец, имя, описание, признак демонстрации, приватность и дата создания. |
| `project_members` | Составной ключ проекта и пользователя; роль `owner`, `admin`, `editor`, `reader` или `guest`. При создании добавляется владелец. Сервер допускает запись для owner/admin/editor, чтение для участников, удаление проекта только для owner. Приглашения и управление ролями через интерфейс пока не реализованы. |
| `worlds` | UUID, проект, имя, описание и дата создания. |
| `characters` | UUID, мир, структурированные поля в JSONB `data`, положительный счётчик `version`. |
| `events` | UUID, мир, поля события в JSONB `data`, `version`. Участники вынесены в отдельную таблицу. |
| `event_participants` | Событие, персонаж и мир. Составные внешние ключи запрещают ссылки на персонажей другого мира. |
| `relations` | UUID, мир, два UUID персонажей, свойства в JSONB `data`, `version`. Самоссылки запрещены; оба персонажа принадлежат тому же миру. |
| `audit_log` | Последовательный ID, проект, пользователь, тип и UUID объекта, действие `create/update/delete`, JSONB-снимок и служебная дата. |

## Поля лора

Карточка персонажа содержит имя, титул или прозвище, вид, пол, годы рождения и смерти, внешность, характер, биографию, мотивацию, способности, секретные сведения и статус `draft/canon`.

Событие содержит имя, тип, начало, необязательное окончание, описание и статус. Участники ссылаются на существующие UUID персонажей. Отношение содержит направление, тип, признак взаимности, необязательные годы начала и окончания и описание.

Исторические годы представлены целыми числами в JSONB. Допустимый диапазон — ±1 000 000 000. Даты PostgreSQL `timestamptz` используются для служебной информации, а не для дат мира. API валидирует содержимое JSONB, длины текстов и временные диапазоны.

## Целостность

Идентичность объектов задаётся UUID. Персонаж не копируется в событие или отношение: используются ссылки. Отношения и участники привязаны составными внешними ключами к одному миру. Удаление персонажа каскадно удаляет его связи и записи участия в событиях, сами события сохраняются.

Удаление проекта удаляет миры и их объекты. Удаление мира удаляет его лор. Аудит сохраняется: при удалении проекта ссылка `audit_log.project_id` становится `NULL`. Аудит предназначен для отслеживания изменений, а не для предоставления API восстановления или исторических состояний.

`projects_demo_owner_idx` допускает один демонстрационный проект на владельца. Индексы на владельцах связей, проектах и мирах поддерживают типовые выборки. Список индексов и правила удаления следует проверять по миграции при изменении схемы.

Обновление персонажа, события или отношения выполняется с ожидаемым `version`. Только совпавшая версия может быть заменена, после чего номер увеличивается. Конкурентная устаревшая правка возвращает 409.

## Хранение и восстановление

Контейнер использует постоянный Docker volume. `docker compose stop db` не удаляет данные. Удаление volume уничтожает базу. Для резервного копирования используйте штатный `pg_dump` и проверяйте восстановление в отдельную базу. Автоматическая политика резервного копирования и интерфейс восстановления не входят в текущий выпуск.

Секреты и данные пользователей нельзя помещать в миграции, README или Git. В production нужны отдельные пароль, права пользователя БД и защищённый доступ к PostgreSQL.
