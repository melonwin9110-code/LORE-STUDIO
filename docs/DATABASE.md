# Модель данных

Автор проекта: **ElpisHeart**. Миграции: `001_initial.sql` — исходная схема, `002_history.sql` — историческая система, `003_family_groups.sql` — независимое родство, `004_portraits.sql` — портреты, `005_timeline_graph.sql` — схема редактора линий, `006_maps.sql` — географические объекты и пространственные редакции, `007_wiki.sql` — исторические статьи и приватные изображения энциклопедии.

## Подготовка и миграции

Docker Compose запускает PostgreSQL 17 с PostGIS. Из корня репозитория выполните `docker compose up -d --wait db`, затем `npm run db:migrate` (`npm.cmd` в PowerShell). Мигратор читает `DATABASE_URL` из `.env`, применяет новые SQL-файлы последовательно и отмечает их в `schema_migrations`. Advisory lock защищает параллельный запуск; каждый файл применяется транзакционно. Применённые миграции не переписываются.

Обновление не требует пересоздания БД. Миграция 002 сохраняет существующие аккаунты, проекты, миры, UUID объектов, текущие значения, номера версий и связи. Для каждого прежнего мира создаются основная линия и стандартный календарь. Первое известное состояние становится исходной редакцией с техническим базовым днём `-1000000000000000`; это не утверждение о реальной дате возникновения персонажа или факта.

## Историческая система

| Таблица | Назначение |
| --- | --- |
| `timelines` | UUID и мир, имя, `parent_id`, зафиксированный `parent_revision`, `fork_day`, текущий `head_revision`, признаки основной и канонической линии. |
| `world_calendars` | UUID и мир, неизменяемое JSONB-определение календаря и признак стандартного календаря мира. |
| `lore_objects` | Стабильный UUID, мир, тип characters/events/relations/maps/map_layers/map_features/wiki_articles и глобальный для этого UUID счётчик конкурентных версий. |
| `lore_revisions` | Неизменяемая редакция объекта: глобальный номер `revision`, линия, день начала действия `effective_day`, `version`, JSONB-содержимое либо логическое удаление, автор и служебное время. |

Глобальный номер редакции — порядок сохранения, день — историческое начало действия. В API номера редакций и дни передаются десятичными строками. `version` объекта остаётся числом для совместимости с API первого выпуска. Изменение в другой ветке не переписывает сохранённый payload исходной линии.

Одна основная линия создаётся для каждого мира. Дочерняя линия закрепляет конкретный head родителя и дату ответвления. При наследовании чтение ограничено этими координатами на каждом уровне; поздние правки родителя и его состояния после даты ответвления не протекают в ветку. Неправленные данные переиспользуются, без копирования всего мира.

Старые таблицы `characters`, `events`, `event_participants` и `relations` сохранены как архив переноса первого выпуска. Новые операции чтения и записи выполняются через `lore_objects`/`lore_revisions`. Прямые изменения архивных строк не являются поддерживаемым способом редактирования текущего приложения.

## Содержимое лора

Персонаж содержит имя, титул, вид, пол, годы рождения и смерти, внешность, характер, биографию, мотивацию, способности, секретные сведения и статус draft/canon.

Событие содержит имя, тип, годы начала/окончания, описание, статус и `characterIds`. Историческое отношение содержит `participantIds` из 2–10 уникальных UUID, произвольный тип `kind`, признак взаимности, годы действия и описание. `fromId`/`toId` сохраняются для совместимости с прежними парами. `familyKind` остаётся совместимым атрибутом старых парных исторических записей; новые общие семейные связи хранятся отдельно. Производные братья и сёстры не записываются отдельными копиями отношений.

Payload событий и отношений сохраняет полный состав UUID участников. Старые неизменяемые пары нормализуются при чтении без перезаписи их исходных фактов. Все ссылки разрешаются в том же мире и историческом состоянии линии. Отметки удаления и обновление связанных записей создаются атомарно. При удалении персонажа событие сохраняется, а участие и отношения корректируются в этой линии; группа сохраняется с оставшимися участниками, если их не менее двух, иначе получает отметку удаления; старые даты и другие линии остаются доступными.

Удаление всего мира или проекта удаляет соответствующий лор. Аудит сохраняется по прежним правилам: при удалении проекта ссылка `audit_log.project_id` становится `NULL`.

## Независимая семья — миграция 003

| Таблица | Назначение |
| --- | --- |
| `world_family_state` | Одно состояние мира: общая `version`, признак `initialized`, время изменения. |
| `family_relations` | UUID связи, мир, два UUID персонажей, `family_kind` parent/adoptive_parent/spouse, описание и версия. `source_relation_id` сохраняет связь с перенесённым историческим фактом. |
| `family_legacy_sources` | Зафиксированные при миграции семейные состояния прежних линий: мир, линия, её имя, исходный номер редакции и JSONB отношений. |

Внешние ключи семейных связей указывают на `lore_objects(id,world_id)`, а не на архивные таблицы первого выпуска. Семья не имеет выбранной линии или дня. Переключение исторического контекста не перезаписывает эти связи. Для представления персонажа используется живой профиль основной линии, затем доступной другой линии; при отсутствии живого варианта может использоваться последний известный архивный профиль, чтобы прежняя семейная ссылка оставалась объяснимой. Общий каталог, в отличие от этого представления семьи, исключает удалённые текущие состояния.

Миграция фиксирует видимые семейные графы всех прежних линий с учётом их редакций и forkDay. Если в одном мире есть семейные записи, сохраняются также пустые исходные семьи других линий, чтобы различие не было пропущено. Старые `lore_revisions` остаются неизменными.

Первый доступ уполномоченного редактора может инициализировать общий граф автоматически, если исходные графы совпадают и проходят проверки. При различиях или несовместимости состояние остаётся ожидающим явного выбора источника; читатель не выполняет такой выбор. Явный импорт использует зафиксированный источник и может выбрать его исторический день. После инициализации обычный импорт прежнего источника отклоняется вместо тихой замены текущей семьи.

Общая версия состояния и версия отдельной связи защищают параллельные изменения. Новые миры получают готовую пустую семью. Исторические familyKind-записи остаются доступны через прежние маршруты, но не синхронизируют автоматически новый граф.

## Портреты — миграция 004

`lore_objects.portrait_version` — отдельный счётчик обновлений портрета. Таблица `character_portraits` содержит `character_id`, `world_id`, `content_type`, обработанные `image_data` типа bytea, ширину, высоту и время обновления. Составной внешний ключ проверяет принадлежность UUID миру.

В БД сохраняется статический WebP, полученный после проверки исходного PNG/JPEG/WebP размером до 5 МиБ. Сервер ограничивает вход до 8192 пикселей по каждой стороне и 20 000 000 пикселей, уменьшает изображение внутри 1200×1200 и удаляет исходные метаданные. URL использует счётчик версии; списки не получают бинарные данные.

Портрет общий для UUID в разных линиях. Логическое удаление карточки в одной линии не стирает его у других вариантов. Явное удаление портрета убирает вложение; удаление всего мира каскадно удаляет его данные. Поскольку файл находится в PostgreSQL, обычный pg_dump включает его, а смена папки исходников не требует копирования отдельного каталога изображений.

## Схема линий — миграция 005

| Таблица | Назначение |
| --- | --- |
| `timeline_graph_state` | Мир, общая версия, JSONB позиций узлов и viewport, автор и время изменения. |
| `timeline_connections` | UUID ручной связи, мир, исходная и целевая линии, тип intersection/influence/travel и подпись. |

Связи ссылаются составными внешними ключами на линии того же мира. Они не заменяют родительские поля `timelines`, не меняют закреплённые редакции и не создают содержимое лора. Позиции, viewport и ручные связи сохраняются атомарно с ожидаемой версией схемы; конфликт возвращает 409. Ручной сюжетный цикл допустим, связь линии с самой собой запрещена.

## Карты и геометрия — миграция 006

География использует общие таблицы исторической системы. Миграция расширяет допустимый `lore_objects.kind` значениями `maps`, `map_layers`, `map_features` и добавляет `lore_revisions.geometry` типа `geometry(Geometry,0)`. Прежние неизменяемые редакции и UUID не переписываются, значения нового столбца у старых фактов остаются `NULL`.

| Вид объекта | Содержимое JSONB-редакции |
| --- | --- |
| `maps` | Название, описание, неизменяемые размеры плоскости, цвет фона и необязательные метаданные `generation`. |
| `map_layers` | UUID карты, название, вид physical/political/custom, видимость, блокировка, прозрачность и порядок. |
| `map_features` | UUID карты и слоя, имя, семантический тип, GeoJSON-геометрия, описание, заливка/обводка/толщина, подпись, необязательные UUID события и территории-родителя. |

Геометрия хранится у каждой живой редакции географического объекта, а не в отдельной изменяемой строке текущего состояния. Карты и слои пространственный столбец не заполняют. Для удаления объекта сохраняется tombstone с `data=NULL` и `geometry=NULL`. Частичный GiST-индекс `lore_revisions_geometry_idx` индексирует ненулевую геометрию.

Ограничение `lore_revision_geometry_valid` принимает непустую валидную 2D-геометрию SRID 0 только типов Point, LineString, Polygon и MultiPolygon. Триггер `lore_map_geometry` при вставке требует пространственную геометрию живого `map_features`, проверяет её топологическое совпадение с GeoJSON payload и запрещает геометрию у остальных видов и удалений. Проверка границ конкретной карты, семантического типа и ссылок выполняется серверной транзакцией. Существующий триггер неизменяемости редакций продолжает запрещать их прямое обновление.

`revision`, `effective_day` и `head_revision` общие с персонажами и событиями. Ответвление закрепляет географию теми же `parent_revision` и `fork_day`. Отдельного счётчика, который позволил бы поздней геометрии родителя попасть в прежнюю ветку, нет. Независимая линия не наследует карты автоматически.

Пакетное сохранение проверяет ожидаемый head линии и версии изменяемых объектов. Слои и объекты записываются атомарно; недопустимый UUID, геометрия или ссылка откатывает весь пакет. Сервер проверяет последующие исторические точки, поэтому удаление слоя/территории не должно оставлять будущие ссылки. Явное удаление карты создаёт исторические удаления её содержимого, сохраняя ранние даты и другие линии. Полное удаление мира или проекта остаётся каскадным удалением по прежним правилам.

В версии 0.5.0 готовая основа сохраняет в payload карты необязательный `generation: { seed, preset, algorithmVersion }`. Новая SQL-миграция не требуется; у прежних карт это поле отсутствует. Полная геометрия результата сохраняется обычными редакциями, а не вычисляется заново при чтении. Изменение названия или фона сохраняет метаданные, ручная правка географии не меняет исходный seed.

Каждый запуск генерации создаёт отдельную карту со свежими UUID, пятью слоями и атомарно записанными географическими объектами. Детерминированные внутренние UUID чистого генератора переназначаются сервером, включая layerId и parentId, чтобы одинаковые основы не разделяли идентичность. Роли, исторический контекст, пространственные ограничения и проверки ссылок остаются общими с ручным сохранением карты. Новая основа не заменяет существующие карты и не требует сброса данных.

Размеры и координаты вымышленной карты измеряются в локальных условных единицах. Географическая долгота/широта и земной SRID 4326 здесь не предполагаются. Объединение и разделение территорий используют PostGIS и возвращают предварительный результат для черновика; без явного сохранения новых редакций не появляется.

## Время и календари

Канонический порядковый день хранится как `bigint`. День 0 — григорианский год 0, январь, день 1; годы могут быть отрицательными. В чистых вычислениях используется BigInt, не JavaScript Date. Служебные даты создания и регистрации остаются `timestamptz`.

Календарь задаёт список `{name, days}`, правило високосных лет или null, подпись эры и `epochOffset` — порядковый день начала его года 0. Определение после создания не меняется. Стандартное григорианское правило учитывает 4/100/400 лет.

Поля годов из первого выпуска ограничены ±1 000 000 000 и остаются григорианскими. Они не преобразуются автоматически при выборе другого календаря. Исторические изменения свойств определяются `effective_day`; годы события и день начала действия его редакции — разные понятия.

## Энциклопедия — миграция 007

`wiki_articles` — новый допустимый вид в `lore_objects`. Авторская статья имеет отдельный UUID и использует общие `lore_revisions`, счётчик `version` и `timelines.head_revision`. Содержимое включает `title`, `summary`, проверенный Tiptap `document`, `category`, `tags`, `knowledge`, необязательный `sourceId` и серверное поисковое представление `searchText`. Последнее строится из разрешённого текста и не задаётся клиентом. Миграция создаёт GIN-индекс `to_tsvector('russian', ...)` для текста редакций. Текущий поисковый запрос вычисляет вектор и ранг после разрешения исторического среза.

Автоматические карточки персонажей, событий, карт и географических объектов вычисляются из доступных редакций; отдельные дубликаты статьи для них не создаются. `sourceId` связывает самостоятельный авторский текст с объектом. Категория, теги и характер знания относятся к статье; метка `secret` не добавляет разрешений и не заменяет членство в приватном проекте.

Сначала разрешаются состояние линии и закреплённые предки, затем выполняются поиск, фильтры и расчёт обратных ссылок. Это сохраняет смысл даты, `parent_revision` и `fork_day`. Новые цели ссылок проверяются в том же мире и контексте; исчезнувшая архивная цель не раскрывает чужое содержимое. Редактирование или логическое удаление статьи не изменяет структурированные факты, старый документ или другую ветку.

| Таблица | Назначение |
| --- | --- |
| `wiki_images` | UUID неизменяемого ресурса мира, `world_id`, `uploaded_by`, `content_type`, обработанные `bytes` (`bytea`), `width`, `height`, `byte_size`, время создания. |

В `wiki_images` хранится только проверенный статический WebP размером до 5 МиБ. Обработка ограничивает вход 8192 пикселями по стороне и 20 миллионами пикселей, уменьшает внутри 2048×2048 и удаляет исходные метаданные. `byte_size` проверяется против реальной длины байтов. Содержание и принадлежность ресурса защищены триггером от перезаписи; при удалении пользователя допускается обнуление `uploaded_by`.

Ресурс остаётся доступен старым версиям статьи после её правок или логического удаления. Прямое удаление ресурса существующего мира запрещено; удаление всего мира каскадно удаляет его изображения. Чтение по URL проверяет текущие права проекта. Байты входят в обычный дамп PostgreSQL, отдельного каталога для переноса при обновлении ZIP нет.

Миграция 007 расширяет ограничения и добавляет новую таблицу/индексы; прежние UUID, версии, payload, пространственные значения PostGIS, портреты, семья и схема линий не переписываются. Обновление выполняется штатным мигратором без сброса базы.

## Целостность и конфликты

- UUID, тип и принадлежность миру стабильны; между мирами ссылки запрещены.
- При записи проверяются сессия, роль, линия и ссылки на действующие объекты.
- PATCH исторического объекта требует `version`, перенос — head цели и при передаче head источника, ответвление — редакцию родителя. Семья и схема линий имеют собственные ожидаемые версии. Сохранение карты проверяет версии объектов и ожидаемый head линии. Статья Wiki требует версию при изменении и логическом удалении. Устаревшее состояние возвращает 409.
- Перенос объектов не изменяет источник и либо применяется полностью, либо откатывается.
- Родственные циклы и известные биологические противоречия общего семейного графа отклоняются. Для совместимых исторических familyKind-записей остаются проверки затронутых исторических точек; неправильные временные диапазоны отклоняются.
- Индексы поддерживают поиск редакций по линии, объекту, дню и номеру сохранения; точный список ограничений — в SQL-миграции.

## Хранение и восстановление

Постоянный том локального Compose — `lore-studio_lore_data` при стандартном имени проекта. `docker compose stop db` сохраняет данные. `docker compose down -v` удаляет том и не применяется для обновления приложения.

Для резервного копирования используйте `pg_dump` в файл и проверяйте восстановление в отдельную БД. Windows-команды без бинарного перенаправления приведены в README. Дампы содержат пользовательские данные; храните их вне Git. Автоматическая политика резервного копирования и пользовательский интерфейс восстановления пока не заявляются.

Для production нужны отдельные учётные данные, права и защищённый доступ к PostgreSQL. Секреты и данные пользователей не помещаются в миграции или документацию.
