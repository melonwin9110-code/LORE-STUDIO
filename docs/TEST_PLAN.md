# План тестирования

Автор проекта: **ElpisHeart**. Текущий план относится к этапам 0–2. Он описывает проверки; результаты конкретного прогона приводятся отдельно в отчёте задачи.

## Подготовка

Используйте отдельную локальную базу `lore_studio_test` для автоматических тестов, доступную приложению через `DATABASE_URL`. Интеграционные тесты создают уникальные аккаунты и проекты, затем удаляют созданные проекты; аккаунты могут остаться в тестовой базе. Браузерные проверки тоже создают данные. Не запускайте их против ценной рабочей базы.

```sh
npm ci
test -f .env || cp .env.example .env
docker compose up -d --wait db
npm run db:migrate
npm run test:prepare
```

`test:prepare` создаёт `lore_studio_test`, если она отсутствует, и применяет миграции. Команда не сбрасывает существующую базу и не удаляет данные. Для другого подключения задайте `TEST_DATABASE_URL`; имя базы должно оканчиваться на `_test`. Тот же URL передайте как `DATABASE_URL` тестовому серверу.

## Автоматические проверки

| Проверка | Команда | Что подтверждает |
| --- | --- | --- |
| TypeScript | `npm run typecheck` | Согласованность типов фронтенда, сервера и тестов. |
| ESLint | `npm run lint` | Статические правила и корректность использования React. |
| Unit | `npm test` | Валидацию, функции безопасности, календари с BigInt и правила семейного графа. |
| Сборка | `npm run build` | Подготовку production-приложения. |
| Интеграционные | `npm run test:integration` | Настоящий API с PostgreSQL, операции лора, права и конфликты. |
| Браузерные | `npm run test:e2e` | Пользовательский сценарий в Chromium и сохранение после обновления страницы. |

Интеграционные тесты ожидают уже запущенный сервер. Запустите отдельный экземпляр на порту 3001 с тестовой базой:

```sh
DATABASE_URL=postgresql://lore:lore_local@127.0.0.1:5432/lore_studio_test npm run dev -- --port 3001
```

В другом терминале:

```sh
TEST_BASE_URL=http://127.0.0.1:3001 npm run test:integration
```

Playwright по умолчанию запускает сервер на порту 3001 с отдельной тестовой БД и ожидает `/api/health`. Если подходящий сервер уже запущен, он может переиспользоваться; явно заданный `TEST_BASE_URL` выбирает адрес сервера. Перед выполнением сценариев общий setup проверяет `testDatabase=true` в ответе фактического сервера. Интеграционные тесты имеют такую же предварительную проверку. Задавайте отдельную БД через `TEST_DATABASE_URL` и передавайте тот же URL как `DATABASE_URL` тестовому серверу. Имя должно оканчиваться на `_test`; одна только строка переменной не заменяет проверку реально обслуживающего запросы сервера.

Установка браузера и прогон:

```sh
npx playwright install --with-deps chromium
DATABASE_URL=postgresql://lore:lore_local@127.0.0.1:5432/lore_studio_test npm run test:e2e
```

Для установленного системного Chromium:

```sh
DATABASE_URL=postgresql://lore:lore_local@127.0.0.1:5432/lore_studio_test CHROMIUM_PATH=/usr/bin/chromium npm run test:e2e
```

`TEST_BASE_URL` позволяет выбрать сервер; он должен соответствовать проверяемому приложению. Playwright сохраняет трассировку и снимки при сбоях. Эти файлы могут содержать тестовые данные и не добавляются в Git.

## Обязательные сценарии API

- Регистрация, повторный email, корректный и неверный вход, состояние сессии, выход и невозможность повторного использования отозванной cookie.
- HttpOnly и SameSite cookie, запрет мутации с посторонним Origin, отсутствие пароля в JSON-ответах.
- Создание приватного проекта и мира, изменение названий, получение данных и удаление.
- Создание демонстрации «Элирия», наличие связанных объектов, идемпотентность повторного запроса и приватность демонстрации.
- Создание и изменение персонажа, сохранение биографии после нового чтения и нового входа.
- Создание события с участниками и отрицательным годом, обновление и удаление.
- Создание взаимного или направленного отношения, изменение описания и удаление.
- Отклонение дробного года, конца раньше начала, самоссылки отношения, повторных участников и UUID чужого мира.
- Скрытие чужих проектов, запрет прямого чтения, изменения и удаления чужих объектов.
- HTTP 409 при устаревшей версии персонажа, события и отношения без потери сохранённой правки.
- Каскадное удаление связей при удалении персонажа с сохранением несвязанных данных.

## Ручная проверка интерфейса

1. Откройте приложение, убедитесь, что видны название Lore Studio и автор ElpisHeart. Переключите светлую и тёмную темы.
2. Зарегистрируйтесь с уникальным email и паролем не короче 10 символов. Выйдите и проверьте повторный вход.
3. Создайте «Элирию» через действие демонстрационного проекта. Убедитесь, что присутствуют несколько персонажей, отношения и события.
4. Создайте новый проект и мир. Переключитесь обратно в демонстрационный мир и убедитесь, что данные не смешиваются.
5. Создайте персонажа, заполнив имя, вид и биографию. Измените биографию, сохраните и перезагрузите страницу.
6. Добавьте событие с годом и одним или несколькими персонажами. Проверьте порядок событий в хронологии. Исправьте описание и перечитайте страницу.
7. Создайте отношение между двумя персонажами. Проверьте направление, взаимность и сохранение.
8. Используйте поиск и мобильную ширину окна. Формы должны оставаться доступными, а поля — иметь понятные подписи.
9. На тестовых данных проверьте отмену и подтверждение удаления персонажа, события, отношения, мира и проекта.
10. Откройте приложение в отдельном профиле браузера с другим пользователем. Приватные проекты первого пользователя недоступны.
11. Сохраните правку из одной вкладки, затем попробуйте сохранить устаревший объект из другой. Должно появиться сообщение о конфликте без тихой перезаписи.
12. Перезапустите только приложение, затем контейнер PostgreSQL без удаления volume. После входа сохранённые объекты должны оставаться доступны.

## Проверки исторической системы этапа 2

Обязательные API- и модульные сценарии:

1. Создать редакции одной карточки на двух датах, прочитать обе и убедиться, что позднее сохранение не стирает прежний текст.
2. Ответвиться от конкретной даты и head. Править родителя после ответвления, включая задним числом; исходные данные ветки остаются прежними.
3. Внести в родителе будущую редакцию до создания ветки. Если её день позже forkDay, она не наследуется веткой.
4. Создать несколько вложенных ответвлений и независимую пустую линию. Проверить ограничение даты и редакции на каждом предке.
5. Изменить или удалить объект только в одной линии. Ранняя дата и другая линия сохраняют прежний объект. Удаление персонажа корректирует связи и участников в той же линии, сохраняя события.
6. Проверить ожидаемый version при двух параллельных сохранениях, ожидаемый head при переносе и редакцию родителя при ответвлении. Устаревший запрос получает 409 без частичной записи.
7. Проверить доступ для всех новых маршрутов, включая календари, историю, сравнение и перенос. Чужая линия и линия другого мира не дают доступ к данным или записи.
8. Сравнить линии, перенести персонажа, событие и отношение со стабильными UUID. Проверить зависимые ссылки, отказ при конфликте без подтверждения, явную замену и атомарный откат при неверном наборе.
9. Создать биологических/приёмных родителей и супругов. Древо обновляется из общей модели; братья и сёстры выводятся без дополнительных записей. Неизвестные родители допустимы.
10. Проверить циклы происхождения на текущей и затрагиваемой будущей исторической точке, непересекающиеся интервалы, рождение ребёнка раньше родителя и после его смерти. Не применять биологическую логику к дате усыновления.
11. Проверить григорианские 1900/2000 годы, год 0, отрицательные годы и большие ±1 000 000 000. Прямой/обратный перевод дат и пользовательские месяцы, високосные циклы и смещение эпохи должны давать согласованные целые дни.
12. Отклонить неизвестный месяц, невозможный день, дробные годы, неверный високосный цикл и некорректные большие числа. Не допускать потери точности JSON.
13. Проверить запрет `revision` в изменяющем запросе и невозможность переписать уже сохранённый payload или родословную линии через API.

Миграция проверяется на отдельной базе с данными схемы 001: сохранить UUID, значения и версии карточек, событий и отношений, применить 002 и сравнить исходное состояние. Участники событий, вход прежним аккаунтом и повторный запуск миграций должны сохраниться. История прошлых эпох из аудита не выдумывается. Перед проверкой обязательна изоляция от рабочей базы; сброс пользовательской БД недопустим.

## Ручная проверка этапа 2

1. На основной линии создайте персонажа и сохраните одну биографию на раннюю дату, другую — на позднюю. Переключение даты должно показывать соответствующий текст.
2. Создайте ветку на раннюю дату. Измените персонажа в ветке; вернитесь в основную линию и проверьте её прежний текст. Затем измените родителя задним числом и снова проверьте ветку после перезагрузки.
3. Добавьте семейное отношение родитель → ребёнок и откройте древо. Дополните второго ребёнка с тем же родителем; проверьте производное родство. Попытка сделать потомка собственным предком должна завершиться понятной ошибкой.
4. Создайте календарь со своими месяцами и високосным циклом. Переведите дату через общий день и выберите её как исторический срез. Проверьте отрицательный год и возврат к стандартному календарю.
5. Сравните линии и перенесите выбранную карточку. При конфликте сохраните отказ по умолчанию; повторите с осознанным подтверждением замены. Источник не должен измениться.
6. Удалите тестового персонажа в одной линии, затем откройте раннюю дату и другую линию. Исторические состояния и связи должны сохраниться.
7. Проверьте те же действия после перезапуска приложения и на мобильной ширине экрана. Выбранные календарь и исторический срез не должны менять смысл григорианских годов событий и рождения.

## Проверка запуска с Webpack и граница Windows-воспроизведения

Для версии 0.2.1 отдельно проверяются `npm run dev` и `npm run build`: обе команды выбирают штатный Webpack через `--webpack`. После запуска нужно открыть приложение в браузере и проверить настоящий запрос к API; готовность процесса сама по себе недостаточна.

У пользователя Windows наблюдалась паника Turbopack Next.js 16.4.3 с `task ... is missing in memory or persistent storage` / `stale reference`, после которой сервер завершался и браузер получал `ERR_CONNECTION_REFUSED`. Успешные миграции на этом скриншоте не требуется повторять ради устранения ошибки сборщика. Рекомендованный обход в старой версии — `npm.cmd run dev -- --webpack`; в обновлённой версии — обычный `npm.cmd run dev`.

Если проверка потребует очистки сгенерированных файлов, сначала остановите сервер и удаляйте только `.next`. Рабочий `.env` и том PostgreSQL должны сохраняться. Облачная машина работает под Linux: результаты её прогонов не являются доказательством воспроизведения исходной Windows-паники или проверки на компьютере пользователя. Фактические команды и результаты 0.2.1 записываются отдельным отчётом; исторические результаты 0.2.0 ниже сохраняются без изменений.

## Отчёт

Указывайте точную команду, завершилась ли она, число выполненных тестов и ошибки. Успешная сборка или открытый порт не подтверждают поведение приложения. Отдельно отмечайте непройденные, пропущенные и незапущенные проверки и конкретную причину. Не обходите проверку TLS, не ослабляйте тесты и не заменяйте тесты формальными успешными проверками.

Геометрия, переносимые архивы и публикация относятся к последующим этапам; их сценарии пока не являются покрытием текущего выпуска.
